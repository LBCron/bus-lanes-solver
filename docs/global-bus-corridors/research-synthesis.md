# DDR routing research and design decisions

The useful change is to plan routing space before repeatedly committing signals to the same attractive channel. DDR layout practice supports planning coherent byte groups, usable carrier layers and escape geometry together. It also requires electrical constraints that a geometric corridor model does not capture. This PR therefore adds advisory global guidance to the existing detailed router and makes a separate, narrowly scoped change that reaches native inner-carrier search earlier.

This synthesis distinguishes vendor guidance, routing research, the implementation at `190325da97253ad7951f9dfd3b0046b4afcb5395`, and future work. Benchmark outcomes belong to the accompanying comparison report.

## What the electrical engineering guidance actually says

The [AMD UG583 General Memory Routing Guidelines](https://docs.amd.com/r/en-US/ug583-ultrascale-pcb-design/General-Memory-Routing-Guidelines) are an additional device-family reference for memory routing and reference-plane requirements. The AMD portal returned its JavaScript application shell during this final verification, so this synthesis does not attribute a newly verified quotation or numerical rule to that page. The concrete recommendations above were checked directly against the downloadable NXP and TI PDFs on 2026-11-18.

The documents do **not** say that every lane should detour backwards, that buses should occupy permanent rectangular regions, or that all DDR devices share one matching rule. Backward or lateral travel is an algorithmic option when it avoids a blocked exit or scarce channel. Its acceptability still depends on the applicable length, skew, coupling, impedance, reference-plane and transition constraints. Pin swapping also requires explicit device rules; this PR does not infer or perform swaps.

## What routing research contributes

The PCB-specific work is particularly relevant because it treats bus planning as more than a collection of shortest paths:

- [Kong, Tan and Wong, *Automatic bus planner for dense PCBs*, DAC 2009](https://experts.illinois.edu/en/publications/automatic-bus-planner-for-dense-pcbs/) describes layer assignment and planar bus routing while considering congestion between components and minimum/maximum bus lengths. Its published results use a large industrial PCB, including experiments with manually supplied layer assignments. Those results do not predict this solver's performance.
- [Wu, Ma and Wong, *An ILP-based automatic bus planner for dense PCBs*, ASP-DAC 2013](https://experts.illinois.edu/en/publications/an-ilp-based-automatic-bus-planner-for-dense-pcbs/) combines bus decomposition, escape routing, layer assignment and global routing. Its abstract explicitly identifies those coupled decisions, explaining why a good global corridor can still fail when package exits or layer assignments are fixed badly.
- [FastRoute](https://onlinelibrary.wiley.com/doi/10.1155/2012/608362) provides the coarse-allocation/detailed-routing separation and congestion-aware alternatives to simple path patterns. [OpenROAD's global-routing documentation](https://openroad.readthedocs.io/en/latest/main/openroad/grt/README.html) exposes routing guides, congestion iterations and layer/region capacity reductions. It explicitly says reduced assumed capacity spreads routes and eases detailed routing. This is evidence for leaving headroom rather than filling every nominal channel.
- [McMurchie and Ebeling, *PathFinder*, 1995](https://janders.eecg.utoronto.ca/1387_2015/readings/pathfinder.pdf) contributes negotiated present and historical congestion: a route can give up a contested resource after its price rises. The final verification endpoint returned HTTP 403, so no new full-text quotation is claimed here. PathFinder is an FPGA-routing method; transferring its congestion idea does not transfer an FPGA performance guarantee to PCB copper geometry.

The NXP/TI PDF text and the two PCB-paper abstracts were directly retrieved for this synthesis. The OpenROAD command descriptions were also checked directly. These sources support the architecture, not a claim that the PR reproduces a published algorithm or its benchmark performance.

## A staged routing process

The following is an engineering synthesis from those sources. It describes a fuller planner than the present API supports:

1. **Establish electrical groups and resources.** Collect DQ, DM, DQS and their constraints; identify command/address/clock groups, valid carrier/reference layers, fixed copper, permitted transitions and any explicitly allowed swaps. Use the controller's rules rather than a universal DDR template.
2. **Plan package escape and byte corridors.** Determine which exits and layers each coherent byte can use. Estimate channel demand from widths and required spacing. Retain room for strobe pairing, vias, later groups and length tuning. Consider difficult outer/longer groups before consuming their scarce resources.
3. **Allocate globally, allowing detours.** Use a coarse graph to price shared channels. A route can initially move sideways or away from its target when that reaches a viable exterior passage. Revisit allocations when demand exceeds capacity; allow a corridor to move instead of treating it as a hard fence.
4. **Route exact copper.** Resolve pad access, clearances, bends and vias with the detailed router. Coarse cell occupancy is only an estimate: a coarse path is neither a legal trace nor proof that a group fits. Feed detailed failures back into allocation instead of repeating the same order indefinitely.
5. **Complete matching and electrical acceptance.** Tune shorter members within reserved space; enforce the declared differential and timing relationships. Validate complete connectivity, fixed-copper preservation, clearances, skew and coupling. Actual DDR sign-off also needs stackup, impedance, return-path and signal-integrity analysis beyond this benchmark.

The most important dependency is between steps 2 and 5. Reserving only trace width can consume the very space needed to add length later. That is why this PR does not steer a request containing any timed bus or differential pair with its untimed coarse model.

## What the final code implements

The new planner works on the ordinary bus members visible in one `negotiateLanes` invocation, on their existing handoff layers. It does not assign whole DDR bytes to new layers. Physical lane demand includes trace width plus clearance. Immutable supplied copper is respected, and terminal package areas are released from the coarse allocation so a tile-level estimate does not dictate detailed package escape.

After the ordinary first detailed sweep detects real contention, an eight-neighbor coarse graph explores sideways, forward and backward paths. The graph has at most 4,096 cells and performs at most four allocation sweeps. Congestion prices spread demand. Uncongested plans, or plans whose overflow does not improve, provide no guides. This bounds coarse work per visible lane; it is not constant total cost independent of lane count or obstacles. Distance-field storage still grows with the number of guided lanes.

A guide adds a nonnegative, bounded spatial cost to a supplementary detailed search. It does not delete legal edges, expand physical length limits or become routed copper. Its cost tapers near packages. Guided searches are restricted to the planned layer, ordinary conflicting candidates, contention visits 2 and 3, and 128 batches of 500 expansions per attempt. Ordinary candidates and active rip-up/history order remain available. A guided candidate changes the result only through a complete compatible assignment.

The whole request bypasses this planner if any bus declares `minLength`, `maxLength` or `maxLengthSkew`, including zero values, or if any differential pair is present. This protects space needed by matching and coupling refinement, including the case where an untimed neighbor could block a timed bus.

The second change addresses a separate search-activation problem: dense, untimed, unpaired native-pad requests with two terminals per signal, at least eight distinct requested members in a bus, and a permitted physical inner carrier enter existing joint negotiation earlier. This lets the established carrier retry happen before serial winding attempts consume most of a byte request's budget. Surface-only requests keep their existing activation path. Multi-terminal decomposition sets `preserveBranchAccess` so a changed trunk order does not obstruct later branch terminals. A64's third-byte public-pipeline regression exercises this narrower path. Its accepted paired timing is reported separately from the guide-quality example.

## Alternatives evaluated and why the change remains conservative

| Approach | Benefit | Limitation or observed result |
| --- | --- | --- |
| Permanent per-bus rectangles or narrow hard corridors | Simple partition; prevents one group from taking every short channel. | Can exclude the only valid detour or package escape, strand unused capacity and require advance knowledge of future groups. Soft, movable guides retain legal alternatives. |
| Route every signal greedily by its individually shortest path | Low initial overhead and often good for easy requests. | Contending signals prefer the same narrow passage; later signals can force repeated retries. The existing first detailed sweep is retained because coarse demand can falsely label legal parallel tracks as congested. |
| Strict coarse plan followed by a few serial hard-copper orders | Reduces detailed expansions on some examples. | The separate experiment completed only two of four capacity-expanded synthetic cases. Its two successes added approximately 28.8% and 9.3% copper, and neither 24- nor 32-lane case completed under the tested caps. It was rejected as the replacement algorithm. See the recorded exploratory diagnostics for exact budgets and scope. |
| Global ILP over decomposition, exits, layers and bus routes | Can express coupled choices explicitly, as PCB research demonstrates. | Requires candidate construction and electrical/resource data absent from the current per-byte request, plus a new optimization dependency and carefully bounded solve. It is a possible future architecture, not this implementation. |
| Earlier joint negotiation for every eight-signal request | Reaches carrier alternatives sooner in A64. | Broad eligibility changed surface and branch exits and regressed later A13/ButterStick access. The final native-inner/unicast guard and explicit branch preservation retain the useful narrow case. |

The synthetic family is not evidence of broad scaling. Under a 1,500-yield diagnostic cap, ordinary main completed 10/12 cases and the supplementary-guide version completed 9/12; added work caused one budget miss. Two common successes used less copper. The original 24/32 pocket geometry also had a necessary single-layer cut capacity of only 23 tracks; failure there cannot establish an algorithmic scaling limit. Capacity-expanded replacements remove that particular obstruction, without proving the full problem feasible.

## What whole-channel planning would need next

Pinned core supplies one eight-DQ byte per phase, freezes previously completed bytes, and leaves DQS/DM to later routing. The bus-lanes solver cannot allocate space for unseen future bytes or reserve their exact strobe/mask/tuning geometry. The current ten-board benchmark validates connectivity, routing checks and native-pad geometry; it is not a full electrical DDR qualification.

A future core/solver interface would need to expose all DDR groups together, including future terminals, their relationships, permitted carrier/reference layers, transition costs and length/delay constraints. A plan could then reserve byte-sized corridors and tuning regions before any byte becomes immutable, with controlled whole-group rip-up when detailed routing disproves an allocation. Capacity estimates should include escapes, via access and tuning headroom, with explicit feedback for detailed failures. This is a proposed extension, not functionality claimed by this PR.

The present change is deliberately narrower: it improves the visible request without assuming that coarse routing can prove detailed feasibility or that an untimed geometric pass establishes DDR electrical compliance.
